# AI 互动大厅 · 架构与知识点

> 西安工业大学云原生俱乐部 · 纳新活动现场用的大屏聊天室
> 1000 人规模压测通过（2 vCPU / 1.7GB 单机，送达率 100.00%）

---

## 一、一句话概括

**一个零第三方依赖的 Go 实时聊天室**：单进程同时提供 HTTP API + 手写 WebSocket + 静态页面，
接 DeepSeek 大模型做「@AI 提问」和「进房欢迎语」，配一套纯 Go 压测工具和前端自动化测试。

## 二、技术栈与硬约束

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | **Go 1.22，仅标准库** | 没有 gin / gorilla-websocket / viper |
| 前端 | **原生 HTML + JS，无框架无构建** | 改完直接刷新生效 |
| 大模型 | DeepSeek Chat API（SSE 流式） | 只用 `net/http` 读 `data:` 行 |
| 存储 | **纯内存**（无数据库） | 重启即清空，活动场景够用 |
| 部署 | Docker 多阶段构建，单镜像 | 二进制 + 静态文件，约 20MB |

**为什么坚持零依赖**：现场网络不可靠（npm/go module 拉不动）、离线可部署、镜像小启动快、
出问题能一行行读懂（`ws.go` 1051 行就是完整的手写 WebSocket 实现）。

## 四、运行时架构

```
                    ┌──────────────────────────────────────┐
   浏览器 ──HTTP──►  │  Go 单进程 (:80)                      │
   (静态页 + API)    │  ┌────────────────────────────────┐  │
                    │  │ net/http mux                   │  │
   浏览器 ──WS────►  │  │  /ws  → 手写 RFC6455 升级       │  │
   (实时消息)        │  │  /api/* → JSON 接口             │  │
                    │  │  /      → 静态文件 (no-cache)   │  │
                    │  └───────────┬────────────────────┘  │
                    │              │                        │
                    │      ┌───────▼────────┐               │
                    │      │  Hub（广播中心）│               │
                    │      │  clients{}      │               │
                    │      │  history[]      │               │
                    │      │  rosterVer      │               │
                    │      └───────┬────────┘               │
                    │              │ 每个连接一个 8192 深队列 │
                    │      ┌───────▼────────┐               │
                    │      │ writePump ×N   │ 批量合并写     │
                    │      └───────┬────────┘               │
                    └──────────────┼────────────────────────┘
                                   │
                          DeepSeek API（仅 @AI 时调用）
```

**核心数据流**：一条消息进来 → `broadcast()` 序列化**一次**得到 `[]byte` → 把**同一个 slice 的指针**
塞进每个连接的队列 → 各自 `writePump` 合并成大批次写出。1000 人在线时，一次广播 = 1 次序列化 + 1000 次入队。

## 五、★ 核心知识点

### 5.1 手写 RFC6455 WebSocket（`ws.go`）

不引第三方库，自己实现协议握手与帧编解码：

- **握手**：校验 `Sec-WebSocket-Key`，用固定 GUID `258EAFA5-...` 做 `SHA1` → `base64` 回 `Sec-WebSocket-Accept`，
  然后 `http.Hijacker` 抢过 TCP 连接
- **帧解析**：FIN/opcode/MASK/payload-len 位运算；支持 7 位 / 16 位 / 64 位三种长度编码；客户端帧必须解掩码
- **opcode**：text / ping / pong / close，分片帧忽略（本场景消息都很短）
- **读写各一条 goroutine**：`readPump` 解析入站，`writePump` 消费队列出站 —— 这是所有 WS 服务的标准骨架

### 5.2 ★★ 背压三级设计（整个项目最重要的一课）

**问题**：1000 人同时进房，每人触发一条 AI 欢迎语，每条欢迎语广播给 1000 人
→ 瞬间 100 万帧。如果无脑往每条连接的队列里塞，就需要几百 MB 缓冲，**小机器直接 OOM 被杀**。

**三级防线**：

| 级别 | 机制 | 参数 |
|---|---|---|
| ① 单连接 | 队列满时**丢最旧**（`enqueue` drop-oldest），保证不阻塞发布者 | 队列深 8192 |
| ② 全局反压 | 所有连接待发帧数之和超过水位 → **暂停发布者**（TCP 自然限速） | 40 万帧 / 最多等 15s |
| ③ 看门狗 | 队列越线后 30s 仍没排空 → 判定为慢消费者，**断开** | 30s |

关键认知：**只加大队列是走不通的**（内存换不来无限缓冲），正确做法是**反压到发送方**，
用有限内存换「不丢消息」。

性能优化：`slowClients` / `queuedFrames` 用 `atomic.Int64` 维护，背压判断是 **O(1) 读计数器**，
而不是每次遍历所有连接。

### 5.3 在线名单：O(N²) → O(N)

朴素做法：每次有人进/出房，就把**全量在线名单**广播给所有人 → 1000 人进房 = 100 万条名单消息。

改成：**每 5 秒合并广播一次**（`onlineBroadcastEvery`），并保留一个 `rosterVer` 版本号。
人数 ≤ 200 时仍在 join/leave 里内联全量名单（兼容旧前端），超过就走合并广播。

### 5.4 批量写：减少系统调用

`writeFrames` 把队列里最多 **64 帧 / 256KB** 合并成**一次 `write()`**。
1000 人在线时下行约 98 万帧/秒，如果不合批，就是 98 万次系统调用 —— 合并后降到约 1.5 万次。

### 5.5 身份识别：刷新/改名都还是「同一个人」

- 浏览器生成 `clientId` 存 `localStorage`，**退出登录也不清**
- 服务端 `usersByClient[clientId] → user`，命中 TTL（**1 小时**）内就判定为同一人
- 效果：刷新页面、改昵称、退出再进 —— 在线人数不会算成两个，AI 也不会重复欢迎
- 隐私：`QQ`/`Phone` 字段打 `json:"-"`，**永远不进任何广播**
- token 传递：`?token=` 查询参数 **或** Cookie（`tokenFromRequest`），方便 WS 和 fetch 共用

### 5.6 AI 流式 + 增量合并推送

欢迎语走 SSE 流式（打字机效果），但**不是每个 token 推一帧**：

```
每 120ms 或攒够 12 个字 → 推一帧 ai_delta
```

一条欢迎语从 ~30 帧降到 ~11 帧，肉眼效果几乎无差别。
`AI_WELCOME_STREAM=off` 可退回「生成完一次性发」（发送帧数降到 1）。

### 5.7 幸运观众抽奖：进房瞬间判定

```
策略关闭（默认）：每个人第一次进房都欢迎一次
策略开启        ：进房那一刻掷骰子（crypto/rand）
                  ├─ 中奖 且 未满额 → 立刻欢迎 + 发编号「幸运用户00x」
                  └─ 没中 / 名额满  → 什么都不做，0 次 AI 调用
```

- 两个参数：**中奖概率**（0~100%）+ **最多中奖人数**（抽满即止）
- **没有定时器、没有手动抽取** —— 判定就发生在进房那一瞬间
- **同一期每人只判定一次**（`participated` map）：反复刷新不能刷概率
- 欢迎记录按「期」隔离（`clientId#lucky#期号`），「开始新一期」后可重新参与
- 中奖编号只定向推送给本人，`/api/me` 才返回，广播里没有

### 5.8 其他工程细节

- **载荷共享**：队列只存 `[]byte` 头，1000 个连接共享同一份序列化结果，不复制内容
- **读缓冲复用**：`bufio.Reader` 复用，避免每帧分配
- **`GOMEMLIMIT=600MiB`**：软内存上限，让 GC 在接近上限时更积极，避免被 OOM Killer 干掉
- **限流**：`RATE_LIMIT_PER_MIN=20` 防 AI 接口被刷
- **知识库注入**：`knowledge.md` 作为唯一事实来源拼进系统提示词，明确要求「不要编造」

## 七、压测方法论（`loadtest/`）

自研纯 Go 压测工具（含手写 WS 客户端），比 wrk/k6 更贴合本场景：

- **真实链路**：真的登录、真的建 WS、真的收满消息才算数
- **送达率**：分母是 `用户数² × 消息数`（每个人都该收到每个人的消息）
- **`-wait-online`**：先等服务端把所有人登记成在线，再开始发 —— 否则压出来的是**自己的竞态**，不是服务端能力
- **分段报告**：登录延迟 / 建连延迟 / 端到端 RTT / AI 首字延迟 / AI 生成时长，都是 P50/P90/P99
- **`-msgs 0`**：只进房不发消息，专门测「进房风暴 + AI 欢迎语到达率」

**实测结论（2 vCPU / 1.7GB）**

| 场景 | 结果 |
|---|---|
| 100 / 300 / 500 / 800 / **1000** 人 × 10 条 | **送达率 100.00%，零丢失** |
| 1000 人 | RSS 294MB，下行约 98 万帧/秒 |
| 500 人 + AI 欢迎全开 | 聊天 100% 送达，500/500 条欢迎语全部到达，RSS 217MB |

**踩过的最大坑**：曾经用公网 IP 压测，流量被云 NAT 发卡弯回，服务端看到的对端是出口 IP，
200 人只连上 183 个、首条 AI 要 1 分 10 秒。**压测一定要打 `127.0.0.1`**，
否则你测的是 NAT，不是服务端。

## 十、值得记住的工程经验

1. **背压 > 缓冲**：小机器上「不丢消息」靠的是反压发送方，不是加大队列
2. **压测要贴近真实链路**：`-wait-online` 这类细节不做，测出来的数字是假的
3. **别打死自己**：`pkill -f` 会匹配到自己的命令行；`kill $!` 在沙箱里杀不掉被包装的子进程 —— 改成**按端口反查 PID**
4. **改了 `.js` 一定要重新 build**：容器跑的是镜像里的 `/app/web`，只改宿主机文件不生效
   （判断方法：看响应的 `Last-Modified` 是不是构建时间）
5. **老用户的数据在浏览器里**：改默认值只对第一次访问的人生效，`localStorage` 里的旧资料要写**迁移逻辑**
6. **一处改名要改一圈**：前端、知识库、提示词、测试断言，漏掉任何一处都会前后矛盾
7. **静默 catch 是 bug 的温床**：`catch(e){}` 吞掉过一个 `ReferenceError`，导致中奖名单一直不刷新却毫无提示
8. **零依赖不是炫技**：现场网络不可靠时，能离线跑起来比什么都重要
