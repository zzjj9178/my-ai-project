# AI 聊天室压测工具

单文件 Go 压测器，**零第三方依赖**（WebSocket 客户端是手写的 RFC6455），专门用来压这个项目。

模拟的真实场景：

1. 并发登录 N 个用户，用户名 `压测1` … `压测N`（对应 `POST /api/login`）
2. 每个用户建立一条 WebSocket 长连接（对应 `/ws?token=...`）
3. **等服务端确认所有连接都登记完成之后**，每人连发 M 条 **普通聊天消息**（`{"type":"msg","text":"..."}`）
4. 消息不带 `@AI` 前缀，**不会触发 DeepSeek 调用**（进房欢迎语除外，见文末）
5. 等消息分发干净，统计延迟 / 吞吐 / **送达率**

## 快速开始

```bash
cd loadtest

# 默认：1000 人 × 10 条无间隔，打本机 http://127.0.0.1
go build -o bin/loadtest . && ./bin/loadtest

# 先小规模验证
./bin/loadtest -users 10 -msgs 3

# 分级压测（100 → 300 → 500 → 800 → 1000），自动抓服务端日志和容器资源
bash run-stages.sh

# 模拟真人节奏：每人每 200ms 发一条
./bin/loadtest -users 1000 -msgs 10 -interval 200ms

# 只进房、不发消息：专门看进房风暴和 AI 欢迎语的到达情况
./bin/loadtest -users 300 -msgs 0
```

> ⚠️ 如果 `go build` 报 `package flag is not in std (...)`，那是 Go 构建缓存不可写导致的**误导性报错**，不是真的缺标准库。
> 指定一个可写的缓存目录即可：`GOCACHE=$PWD/.gocache go build -o bin/loadtest .`（`run-stages.sh` 已经这么做了）

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-base` | `http://127.0.0.1` | 被压测地址，也支持 `https://`（自动走 wss） |
| `-users` | `1000` | 并发用户数，登录名 = 前缀 + 序号 |
| `-msgs` | `10` | 每人发送的普通聊天条数；**`0` = 只进房不发消息**（单独压进房风暴 / AI 欢迎语） |
| `-interval` | `0` | 同一用户两条消息之间的间隔；`0` = 无间隔极限压满 |
| `-name-prefix` | `压测` | 登录名前缀 → `压测1` … `压测1000` |
| `-school` / `-major` | `压测大学` / `压测专业` | 登录时填的学校 / 专业 |
| `-login-parallel` | `50` | 登录并发度 |
| `-connect-parallel` | `200` | WebSocket 建连并发度 |
| `-wait-online` | `30s` | 开压前等待服务端确认所有连接已登记的最长时间 |
| `-samples` | `20` | 抽样测「消息回环延迟」的客户端数 |
| `-settle` | `0` | 全部连上后、开压前额外等待多久 |
| `-drain-quiet` | `5s` | 所有类型的帧都安静这么久就判定结束 |
| `-drain-timeout` | `300s` | 收尾最长等待 |
| `-out` | 空 | 报告 JSON 输出路径 |
| `-label` | 空 | 报告标签 |

### 为什么要有 `-wait-online`

收到 `101 Switching Protocols` 只代表**握手**完成，服务端把它登记进 hub 还有微小延迟
（要序列化全量在线名单和历史、再进 hub）。不等待就开压的话，后登记的客户端会漏掉前面广播的消息
—— 压出来的「送达率」其实是在测压测器自己的竞态。实测这一项能让同一份代码的结果从 93% 变成 100%。

## 报告怎么读

```
[送达率 —— 核心指标]
  总下行应有/实收 : 10000000 / 10000000（每条消息广播给所有人）
  送达率      : 100.00%    丢失: 0 条
```

- **总下行 = 人数 × 人数 × 每人条数**。1000 人 × 10 条 = 1 万条上行，但每条都要广播给 1000 个连接，
  所以服务端要推 **1000 万帧**（约 2.5GB）。这才是真正的压力点，不是「1000 人登录」。
- **送达率 < 100%** 对应服务端日志里的 `发送队列已满，丢弃消息`（`hub.broadcast` 在队列满时会兜底丢弃）。
- **掉线/读错误 > 0** 说明服务端被压崩或 OOM 了。
- **[消息类型拆解]** 统计的是**收到的帧数**，AI 的帧同样会广播给每个客户端，
  所以 1 条 AI 回答在 N 个客户端上就是 N 倍的 `ai_delta`。

## 实测结果（2 vCPU / 1.7GB 单机）

| 档位 | 修复前送达率 | 修复后送达率 | 服务端内存 |
|---|---|---|---|
| 100 人 × 10 条 | 29.93% | **100.00%** | 38 MB |
| 300 人 × 10 条 | — | **100.00%** | 68 MB |
| 500 人 × 10 条 | — | **100.00%** | 130 MB |
| 800 人 × 10 条 | — | **100.00%** | 265 MB |
| 1000 人 × 10 条 | 80.57% | **100.00%** | 294 MB |

压测机和服务端在同一台 2 核机器上，下行峰值约 **98 万帧/秒（167 MB/s）**，全程零掉线。

## 服务端为通过 1000 人做的修复

都在 [backend/ws.go](../backend/ws.go)，细节见代码注释：

1. **修掉握手期死锁**：旧代码先 `h.add(client)` 再启动 `writePump`，中间还夹着阻塞写。
   只要这个窗口里有 ≥ 队列容量条广播灌进来，阻塞写就永久卡死（`writePump` 永远启动不了），
   该连接收不到 `init`、`readPump` 也不启动，连接和 goroutine 一起泄漏。
   现在改成「先直接写 init/history → 起 writePump → 再进 hub → 再广播」。
2. **批量写帧**：`writePump` 把队列里堆积的多帧合并成一次 `Write`，系统调用降一个数量级。
3. **队列满不再静默丢弃**：改成全局 + 单连接双水位背压（待发积压越线时让发布者等，反压回发送方 TCP），
   配 O(1) 水位判断（早期版本遍历所有连接算最大队列深度，1000 人时被重试放大成平方级开销）。
4. **慢消费者看门狗**：某条连接积压超过 30s 仍未排空就主动断开，避免一条死连接拖住整个房间。
5. **在线名单合并广播**：`join/leave` 不再每次携带全量在线名单（O(N²) 流量），
   改由服务端每 5s 合并成一条 `{"type":"online"}` 下发；前端 `common.js` 已同步兼容。
6. **丢弃日志限速**：每条丢弃都打日志在 1000 人房间里能把 CPU 打满，改成每连接 5s 最多一行。
7. **读帧缓冲复用 + `GOMEMLIMIT`**：避免每帧 `make`，并让 Go 堆有上限，防止连续压测时堆不还给 OS 导致 OOM。

## 服务端可调参数

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `WS_SEND_BUFFER` | `8192` | 每连接待发队列长度（只存切片头，载荷共享，实际每连接约 196KB） |
| `WS_BACKLOG_HIGH_WATER` | `400000` | 全局待发帧数水位线，超过就让发布者等待 |
| `GOMEMLIMIT` | `600MiB` | Go 堆上限，小内存机器上防 OOM |
| `AI_WELCOME` | `on` | 进房自动 AI 欢迎语开关 |
| `AI_WELCOME_STREAM` | `on` | 欢迎语是否流式：`on` = 打字机效果（增量每 120ms 合并推送一次）；`off` = 生成完一次性发 |
| `RATE_LIMIT_PER_MIN` | `20` | @AI 调用限流（**不作用于欢迎语**） |

## 注意事项

- 压测前请确保房间里没有别的客户端（比如你自己开着的浏览器页面），否则 `-wait-online` 会被提前满足。
- 压测机和服务端在**同一台机器**时两者抢 CPU，结果偏悲观；要拿准确数字请把压测器放到另一台机器上。
- `run-stages.sh` 每档之间会等 `/api/health` 的 `online` 回到 0 再开始，避免上一阶段的残留连接污染下一阶段。
- **AI 欢迎语**：服务端在每个人进房时会异步调 `sendWelcome()`，也就是**每登录 1 个人就花 1 次 DeepSeek 调用**。
  1000 人进房 = 1000 次真实付费调用，还会产生约 3 倍于聊天流量的 `ai_delta` 广播。
  做纯聊天容量验收时建议压测期间 `AI_WELCOME=off`。

## 管理后台（幸运观众）

访问 `http://<host>/admin`，账号 `admin` / 密码 `qwer1234`（可用 `ADMIN_USER`、`ADMIN_PASS` 覆盖）。

| 策略 | 行为 |
|---|---|
| **关闭**（默认） | 每个人第一次进房都会被 AI 欢迎一次 |
| **开启** | **进房瞬间掷骰子**：按「中奖概率」判定，中了立刻欢迎 + 发「幸运用户00x」编号；没中不触发任何 AI |

中奖欢迎语是**流式**的（打字机效果），但增量做了**合并推送**（每 120ms 或攒够 12 字推一帧），
所以一条欢迎语约 10 帧而不是 30 帧；不想流式就设 `AI_WELCOME_STREAM=off`。

两个可调参数：

- **中奖概率**：0% ~ 100%（滑块，另有 1/5/10/30/50/100% 快捷按钮）
- **最多中奖人数**：抽满即止（上限 1000）

特点：

- 判定发生在**进房那一刻**，没有定时器、没有手动抽取，跟进房顺序无关（加密随机数）
- 实际中奖人数 ≈ 进房人数 × 概率，且不超过「最多中奖人数」
- 管理端实时显示：当前在线、本期进房人数、已中奖/上限、**实际中奖率**、**中奖名单**（编号/昵称/学校/时间）
- 中奖者在自己「个人中心」里能看到编号，收到推送时无需刷新
- 抽奖状态存在内存里，**容器重启会清空**；「开始新一期」可手动清空名单
